# Decisions and rules

For developers and agents who continue the work. Each row says what was decided, why, and what it costs. The second half lists rules that must not be broken, because the checks and tests exist to keep them.

## Decisions

| Decision | Why | What it costs |
| --- | --- | --- |
| **A small static site builder in plain Node, no web framework** (the architecture document planned Next.js and a headless CMS) | Package installs were disabled in the environment this was built in, so no framework or CMS could be installed. A static builder with plain-text content also gives the fastest possible pages and the smallest attack surface. | No no-code editor (PUB-7). Staff edit text files. Adding one is the main item for the next stage; content files are Markdown with simple details, which any CMS can read. |
| **Content lives in files, and the build is the safety net** | Every rule staff must follow (consent, dates, money split, alt text) is enforced where they edit, with a plain-language message, instead of being discovered on the live site. | Edits need a rebuild to go live. |
| **Dates are written in the site's own time zone and stored as exact instants** | A deadline means one moment for everyone. Every date and time shown names its zone; machine-readable `<time>` is always UTC. | `timezone` in `site.json` must be set properly. It is a placeholder (UTC) now. |
| **A deadline closes one minute late** (`closesAt = deadlineAt + 60 s`) | A deadline of 23:59 should stay open through 23:59:59. Someone submitting at 23:59:30 must not be turned away. | The Phase 3 application form **must use `closesAt`** from `src/lib/dates.mjs`, not `deadlineAt`. A deadline must be written with a time. |
| **Open or closed is computed at build time and again in the browser when a program page loads** | The site works with no script and no server logic. The browser re-check makes a program page right whenever it is opened, even from an old build. It does not change a page that is already open, which would be confusing for someone reading it. | Lists and the home page are right only as of the last build. Rebuild hourly (see operations). |
| **A production build refuses unfinished content** | Sample text must not reach a public site. The build lists every file and writes nothing. | A first production build will refuse until the Foundation supplies its own text. That is intended. |
| **Stories need `consent: true` and a recorded date; they are otherwise silently left out with a warning** | Student privacy. Publishing is a decision a person records, not something that happens because a file exists. | A forgotten consent line means a story does not appear. The warning names it. |
| **No CAPTCHA** | CAPTCHAs exclude users of assistive technology, and most send visitor data to a third party. Instead: a hidden field, a minimum fill time, a link limit, and per-address and overall rate limits. | Motivated spammers may get through. If abuse appears, add a privacy-respecting CAPTCHA at the gate in `server/forms.mjs` (`gate()`), and keep the other measures. |
| **Hidden-field hits are kept privately, not discarded** | A browser that auto-fills the hidden field would otherwise lose a real person's message without a word. | Staff must glance at `data/held/` now and then. Nothing in it is emailed. |
| **Email goes to an outbox folder, not to a provider** | No mail provider has been chosen. The flow, including double opt-in, is built and tested against the outbox. | Messages are not delivered until `server/mail.mjs` is connected. |
| **Newsletter links are signed, not stored** (HMAC tokens; only confirmed subscribers are kept) | An unconfirmed address is never stored, so a stranger's address typed in by a prankster leaves no trace. | Replacing `data/secret.key` breaks links already emailed. Links open on a plain GET, so make them two-step when real email is connected (scanners open links). |
| **Strict content security policy, no inline code, nothing from other sites** | Protects visitors and the Foundation from injected scripts. The one inline script (a single line that marks scripting as available, so the menu never flashes open on a phone) is allowed by its hash. | Third-party widgets (maps, video, chat, analytics) cannot simply be pasted in. Each needs a deliberate policy change and a consent step. |
| **Markdown links are allowlisted** (`/…`, `https`, `http`, `mailto`, `tel`) and raw HTML is shown as text | Staff text can never carry a script, even by mistake. | An unusual link scheme appears as plain text. |
| **Analytics are off, and when enabled load only after the visitor accepts** | NFR-3. A choice banner appears only when analytics are enabled in `site.json`, and no analytics script is in the page until it is accepted. | None until analytics are chosen. A production build refuses analytics without an `https` script address. **Before enabling analytics, add a visible way to change the choice later** (withdrawing consent must be as easy as giving it); it is not built yet. |
| **Colors come from `site.json` and are checked for contrast at build time and again as drawn in a browser** | The brand will change; accessibility must not depend on remembering to check. 35 color pairs are checked in both themes. | Some colors the Foundation may like are refused. The message names the pair and the ratio. |
| **Yellow is used only for deadlines, amounts and the students' share** | The design's one idea: yellow means "this matters to you". Overuse would erase that. The warm amber on the donor tiles is a different color and means giving only. | New features must follow the rule. See the design plan. |
| **One typeface, Inter, self-hosted, cut to Latin, with `font-display: optional`** | No third-party request, a small download (55 KB for two weights), and **no layout shift at all** (measured 0.000). It is the closest free match to the mockup's face. | On a very slow first visit, the first page may show a system sans-serif and later pages show the web font. There is no italic file. Pashto and Dari need new font files. A replaced font file needs a new file name, because fonts are cached for a year. |
| **The look follows the Foundation's mockup; the yellow marker and the ruler were kept** | The mockup is the Foundation's direction. The marker and the ruler answer real questions (when is the deadline, what share reaches students) and make the site specific. | Cards are used only where a thing is a unit, so article and legal pages stay plain. See the design plan. |
| **Icons, not photos, stand for people** | The Foundation's request. Icons need no consent, cannot go stale and are drawn in the page (`src/icons.mjs`), so there is nothing to download. | Every icon is `aria-hidden`; a page check fails the build otherwise. The words carry the meaning. |
| **The pictures and the connector have no words; the two dashed lines to the connector have arrowheads** | The Foundation removed the icons from the flow and then every label. In the third round it asked for the line from a reference photo to be used between the students, connector and donors cards, and that line ends in an arrowhead and starts with a dot. So the lines now point from the donors to the connector and from the connector to the students. | The arrowheads say which way the money and the help go, which the earlier version left unsaid on purpose. If the Foundation would rather say nothing about direction, remove the `.link::after` rule (the arrowhead) from `src/styles.css`. The lines carry no information the page lacks: they are `aria-hidden`. |
| **The hero's pictures, figure cards and lines are one quiet background layer** | The Foundation's second round of feedback: the students, Foundation and donors picture, and the two cards of figures, "should be regarded as texture of the background, together with the decoration lines" and "not distract viewers' attention". So: no words in the pictures, colours mixed down towards the page colour, a pale one-pixel edge, no shadows, and the headline and buttons are the only loud things. The third round made the figure cards smaller (the same width as the pictures, 14.5 rem) and quieter again: small type (0.75 rem) all in the secondary ink. The pictures and the lines are `aria-hidden`; the cards are an ordinary heading and list. | The pale colours are chosen by eye, within the contrast rules (every piece of text is still checked as drawn, and anything paler than the secondary ink on the cards fails). The pictures, connector and lines are left out below 64 rem, where they would only push content down. |
| **The four-card arrangement and the headline's size come from a reference photo; nothing else does** | The Foundation sent a photo of another landing page and asked for exactly three things from it: four cards around a large centred headline (the lower two set in a little), the headline's placement and size, and the style of its connecting line. Its colours, type, wording and imagery were not copied. | Four cards in the corners is a common arrangement; what is specific to this site is in the cards (figures from the Foundation's own records, a picture with no words). Below 64 rem the arrangement is not used, because the corner cards need the width. |
| **The two figure cards read the newest year's content files** (students by program from `content/data/impact-YYYY.md`; total donations and transactions from `content/reports/YYYY.md`) | The numbers must come from the same files as the rest of the site, so they cannot drift from the Impact and Finances pages. A card whose source has no list is left out, and never falls back to an older year, so old figures cannot pass for current ones. | Staff must keep `byProgram` adding up to `students`, and give `income` and `transactions` in the newest report; the build says what is wrong in plain words. The cards never say "sample": the staging strip and the production gate cover that. |
| **The lines join only the students picture, the connector and the donors picture, and are built in HTML and CSS** | The Foundation's third-round request: use the reference photo's line between donors, connector and students, "not the data cards". Two lines run down the sides of the page (outside the text, into the footer), a quarter-circle branch from each turns in under its picture (one small inline SVG, mirrored in CSS), and a dashed stretch with a dot and an arrowhead runs from each picture to the connector. Everything is placed from the same few variables (`--track`, `--side`, `--inset`, the picture widths), so the lines stay attached when a size changes. `z-index: -1` and an isolated hero mean a line goes behind a card, never through it. | The second round's SVG (the weaving lines, with `translate(548 -251)` to line them up) is gone; `deco` and `decoSoft` are still the colours. Below 64 rem only the two side lines remain, half a rem in from the edges. On the home page only; another page would need its own arrangement. |
| **Money in and out is shown four ways** (arrow, filled or outlined tile, + or −, and "Received" or "Paid out" for screen readers) | Colour must never be the only signal, and the figure cards are quiet, so the signs are redundant on purpose. | The amount is stored without a sign; `direction` decides. |
| **Page titles use the short name** ("Programs \| Khwarizmi") | The full name made 60 to 90 character titles that search results cut off. The full name is still used for sharing and the feed. | `shortName` in `site.json` must be set. |
| **Styles are right-to-left ready** (start and end, not left and right) | Pashto and Dari are planned. Changing every rule later would risk breaking pages that were already approved. | The language switch, translated text and Arabic-script fonts are still to do. |
| **High-contrast mode is checked** | Windows high-contrast mode removes background colors, which silently erased the finances chart and the logo tile. A browser check now fails if a bar, swatch or card loses its shape, or if the lines between the cards show. | New shapes that are only a background need a system color in the `forced-colors` block of `src/styles.css`. |
| **Everything under `/assets/` is cached for a year, and its address carries a fingerprint** (`?v=…`) | Fast repeat visits. A rebuilt stylesheet, script, logo or share image reaches returning visitors because its address changes. | The `caching` check fails the build if a new asset is referenced without one. |
| **One place for each fact** | The public address and the staff mailbox are read from `content/site.json` by the server too. Environment variables override. | A value still in `[[brackets]]` is treated as not set. |
| **Checks have their own tests** (`check.test.mjs` breaks a good build 60+ ways and confirms each is caught) | A check that cannot fail is worth nothing. | When a check is added, add a case that breaks it. |
| **Placeholders: UTC, `en-US`, USD, example addresses** | The Foundation's country, legal entity and currency were not given. Nothing was guessed from an email address or a name. | All must be confirmed. See the status document, "Questions for the Foundation". |

## Rules that must not be broken

1. **Never publish a story without recorded consent.** Do not weaken the check or default `consent` to true.
2. **The Phase 3 deadline logic must call `programState` / `closesAt`** from `src/lib/dates.mjs`, so the form and the page never disagree.
3. **No script, style or font from another site, no inline event handlers, no inline styles.** `npm run check` fails if any appear. If a third party is needed, change the policy in `src/lib/security.mjs` on purpose, document why, and put it behind consent.
4. **No cookies or tracking before consent.** The site sets no cookies. The only thing it stores in the browser is the visitor's analytics choice (`analytics-consent`, in local storage), and only when analytics are enabled. Anything else added must be strictly necessary or wait for consent.
5. **Never serve or commit `data/`.** It holds addresses, messages and the signing key.
6. **Colors, type sizes and spacing go through the tokens** in `content/site.json` and `src/styles.css`, so the contrast checks cover them.
7. **Every image has a description; every table a caption or name; every form field a label.** The checks fail otherwise.
8. **Deploy only from a successful production build.** An old staging build must never be mistaken for a finished one.
9. **Keep the budgets.** Page 60 KB, stylesheet 30 KB, script 8 KB, fonts 160 KB, first view 140 KB, all compressed. Today the stylesheet is about 7.6 KB and the heaviest first view about 68 KB.
10. **A new rule for staff content gets a plain-language message and a test.**

## Where Phase 3 and 4 plug in

- The Apply buttons point at `/apply/start/`, a stub page (`content/pages/apply-start.md`, `stub: true`). Replace it with the application flow.
- New server routes go in `server/server.mjs` next to the form routes. Reuse `gate()` and the rate limiter in `server/forms.mjs` for any public form, and the same-origin check for any post.
- Private uploads (NFR-4) must be stored outside `dist/` and `data/` public reach, encrypted, and served only to signed-in roles.
- The Donate page is a stub; payments need a provider chosen first (open question).
- Anything that adds a database moves `data/newsletter.json` into it, and brings the retention and deletion rules of NFR-2 with it.
